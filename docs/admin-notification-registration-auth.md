# مصادقة تسجيل جهاز إشعارات الأدمن

هذا التغيير يخص `POST /api/register-admin-token` فقط. لا يغيّر قواعد Firestore أو الدفع أو checkout أو طريقة إرسال الإشعارات أو التوكنات المحفوظة مسبقاً.

## التغيير

- يجب إرسال Firebase ID token صالح للمستخدم الأدمن في `Authorization: Bearer <Firebase ID token>`.
- يتحقق السيرفر من التوكن عبر `verifyAdminIdToken` الموجود بالفعل، ثم يطابق UID الأدمن ويرفض الحساب المعطّل. توكن FCM وUID داخل JSON ليسا وسيلة مصادقة.
- يبقى `OPTIONS` متاحاً بلا تسجيل دخول لتوافق Capacitor، وتسمح ترويسات CORS بـ`Authorization`. السماح بالـorigin ليس بديلاً عن المصادقة.
- تبقى الكتابة بحساب الخدمة بعد نجاح المصادقة فقط. الفشل لا يسجل جهازاً، ولا يعرض توكنات أو تفاصيل داخلية في الاستجابة أو السجل.

## ترتيب الدمج والإطلاق

الفرع مبني مباشرة على `main`، ولا يعتمد على PR آخر مفتوح. لا يلزم دمج PR #2 أو #4 أو #6 قبله.

**قبل دمج هذا PR ونشره:**

1. تحقق من وجود `FIREBASE_SERVER_API_KEY` على السيرفر وربطه بنفس مشروع Firebase الذي يسجل فيه الأدمن الدخول. هذا المتغير تستخدمه آلية التحقق الحالية بالفعل. لا تضفه إلى الكود أو إلى متغير `NEXT_PUBLIC`. لم تُفحص إعدادات الإنتاج في هذا العمل.
2. افحص كود تطبيق أندرويد/Capacitor الخارجي، فهو غير موجود في هذا المستودع. عليه الانتظار حتى تسجيل دخول الأدمن، والحصول على Firebase ID token من الجلسة، ثم إرساله في ترويسة `Authorization` مع نفس JSON الحالي `{ token, platform }`. في Firebase Web SDK يكون مصدره `await currentUser.getIdToken()`، وليس FCM registration token أو refresh token أو مفتاح حساب خدمة. التطبيق الذي يستخدم native Firebase SDK يأخذ ID token من جلسة ذلك الـSDK نفسها.
3. جهّز تحديث التطبيق واختبره على بيئة تجريبية أولاً. يمكن للعميل المحدّث إرسال الترويسة قبل نشر حماية السيرفر، لذلك الترتيب الآمن هو العميل المتوافق أولاً، ثم هذا PR والسيرفر. إن تعذّر تجهيز العميل، اعتبر فشل تجديد/تسجيل أجهزة أندرويد القديمة بعد النشر أثراً مقصوداً يجب الموافقة عليه، وليس توافقاً مؤكداً. لا تترك مساراً مجهولاً كحل مؤقت.

توكنات الأجهزة المحفوظة لا تُحذف بهذا PR؛ الإرسال إليها لا يتغير. لكن تسجيل جهاز جديد أو تجديد توكنه من عميل لا يرسل المصادقة سيرجع 401. هذا لا يثبت استمرار الإشعارات على كل جهاز بعد تدوير التوكن. تسجيل الويب الحالي مباشر عبر Firestore بجلسة الأدمن، وليس عبر هذا endpoint، ولم يتغير.

## اختبار القبول

على بيئة اختبار ومشروع/أجهزة اختبار فقط، من دون استخدام أوردر عميل حقيقي:

- `OPTIONS` من `https://localhost` مع طلب السماح بـ`Content-Type, Authorization`: يرجع 204 والترويسات المطلوبة.
- POST بلا Bearer، أو بتوكن منتهي/غير صالح، أو مستخدم عادي: يرجع 401 ولا تُضاف وثيقة.
- Firebase غير متاح أو مفتاح التحقق ناقص: يفشل مغلقاً، ولا يُسجَّل جهاز. راقب 401 لتفريق مشكلة إعدادات عن غياب جلسة العميل.
- جلسة الأدمن الصحيحة مع FCM token تجريبي: 200 ثم وثيقة واحدة صحيحة في `adminTokens` بمشروع الاختبار.
- JSON تالف أو token ناقص بعد المصادقة: 400. فشل التخزين: 500، لا نجاح وهمي.
- من أندرويد: سجّل الدخول، فعّل الإشعارات، أغلق التطبيق وافتحه، ثم جرّب تجديد التوكن. اختبر استقبال إشعار تجريبي في المقدمة والخلفية. من الويب: تحقق أن التسجيل المباشر والاستقبال ما زالا يعملان.
- بعد الخروج من حساب الأدمن يجب ألا يستطيع التطبيق تسجيل أو تجديد جهاز عبر هذا المسار.

اختبارات الوحدة تحاكي رد Firebase والتخزين ولا ترسل إشعارات ولا تكتب بيانات حقيقية. نجاحها أو نجاح البناء لا يحل محل الاختبار الفعلي لتطبيق أندرويد أو إعدادات الإنتاج.

هذه الحماية تمنع التسجيل الجديد غير المصرح به عبر هذا endpoint فقط. لا تحذف أي توكن سابق مشبوه، ولا تغلق قراءة `adminTokens` العامة في قواعد Firestore المرسلة، ولا تعالج بقية APIs. مراجعة القواعد وحصر الأجهزة الحالية عمل منفصل يحتاج نطاقاً واختباراً خاصين به.
