# صفحات الموظفين عبر API السيرفر (Staff pages via server APIs)

> **المشكلة:** صفحات الطلبات والعملاء والقسائم كانت تقرأ Firestore مباشرة
> من المتصفح، وقواعد Firestore الحيّة تسمح بهذه القراءة للمالك فقط —
> فكان أي موظف، حتى بدور أدمن، يرى قائمة فاضية أو رسالة خطأ.
> صفحة الرئيسية كانت تعمل لأن أرقامها تأتي من API السيرفر.
>
> **الحل:** نفس النمط المتبع في `/api/admin/dashboard-stats` — الصفحات
> الأربع تقرأ/تكتب عبر API routes على السيرفر (Service Account
> فيتخطى القواعد)، والأدوار تُفرض بـ `verifyAdminPermission` فقط.
> **لا يوجد أي تغيير في Firestore Rules في هذا التغيير.**

## الخطأ المُتحقَّق حيًا (صفحة القسائم)

في صفحة الشحن وأكواد الخصم ظهر للموظف نصًا:

> "فشل تحميل البيانات: Request failed with error: Missing or insufficient permissions."

السبب في الكود: `promotions/page.js` كانت تنفذ
`getDocs(collection(db, "promoCodes"))` من المتصفح، وقراءة `promoCodes`
في القواعد الحيّة للمالك فقط. الكتابة (إنشاء/تعديل/حذف كود) كانت
مرفوضة أيضًا لعدم وجود قاعدة كتابة لها. هذا المسار (`GET/POST/DELETE
/api/admin/promotions`) يصلح القراءة والكتابة معًا.

ملاحظة عن مشاهدة لاحقة: المستخدم أفاد بعدها أن العروض/القسائم "ظهرو"
بحساب تجريبي بدور أدمن — لكن غير مؤكد إن كانت المشاهدة من صفحة
القسائم (`promoCodes`) أم من داخل صفحة العروض (عرض `coupon_fixed`
في كولكشن `offers` وقراءته عامة)، أو أن الخطأ السابق كان جلسة قديمة.
لذلك يبقى الاختبار الحي لكل دور بعد النشر هو ما يحسم الأمر، ولا يُسحب
هذا الإصلاح بناءً على تلك المشاهدة.

## حالة قائمة العروض

حالة قائمة العروض عند الموظفين **غير مؤكدة بعد** (لم يُفد المستخدم
إن كانت تحمل أو فارغة أو تظهر خطأ). قراءتها عامة في القواعد، لذلك
بقيت القائمة تقرأ من المتصفح كما هي. ما أُصلح هنا هو **الكتابة**
المؤكدة في الكود: حفظ/تفعيل/حذف العرض وحفظ قاعدة الشحن المجاني
كانت تستخدم `setDoc/updateDoc/deleteDoc` من المتصفح، وهي مرفوضة
للموظفين (كتابة `offers` و`settings` للمالك فقط).

## الـ endpoints الجديدة

| المسار | الصلاحية | الوظيفة |
|---|---|---|
| `GET /api/admin/orders?tab&limit&offset` | `orders.view` | قائمة الطلبات مرتبة بـ "Created at" تنازليًا |
| `GET /api/admin/orders?email=` أو `?phone=` | `orders.view` | طلبات عميل واحد (تستخدمها صفحة العملاء عند الحذف) |
| `GET /api/admin/customers?tab&limit&offset` | `customers.view` | قائمة العملاء مرتبة بـ `last_active` تنازليًا |
| `GET /api/admin/promotions` | `promotions.edit` | قائمة أكواد الخصم |
| `POST /api/admin/promotions` | `promotions.edit` | إنشاء/تعديل كود (`{ code, data, create }`) |
| `DELETE /api/admin/promotions?code=` | `promotions.edit` | حذف كود |
| `POST /api/admin/offers` | `offers.edit` | إنشاء/تعديل عرض (`{ offer, editingId, environment }`) |
| `PATCH /api/admin/offers` | `offers.edit` | تفعيل/إيقاف عرض (`{ id, active }`) |
| `DELETE /api/admin/offers?id=` | `offers.edit` | حذف عرض |
| `POST /api/admin/offers/shipping-rule` | `offers.edit` | حفظ قاعدة الشحن المجاني (`{ rule, environment }`) |

- التصفح بالإزاحة (`limit`/`offset`) بدل مؤشر مستند Firestore.
- `serverOrderStore.query` امتد اختياريًا بـ `orderBy` و`offset`
  وسماح بغياب الفلاتر (لسرد كولكشن كامل) — متوافق رجعيًا مع كل
  الاستدعاءات الحالية.
- الكتابة تتم بـ `serverOrderStore.commit` مع شرط إصدار المستند
  (version precondition) للتعديلات، و`create: true` للإنشاء.
- التحقق من الحقول يتم على السيرفر (نفس قواعد الصفحات)، والسيرفر
  يبني المستند المخزّن من الحقول المتحقَّق منها فقط.

## ما الذي لم يتغير (بقي من المتصفح عمدًا)

- تعديل حالة التجهيز/الدفع في صفحة الطلبات: كتابة `Orders`
  مسموحة في القواعد (`create/update if true`) فتعمل للموظفين أصلًا.
- حذف الطلبات/العملاء وزر "تحديث الأرشيف" (`fixOldData`): ما زالا
  من المتصفح — الحذف مرفوض للموظفين في القواعد حتى بعد هذا التغيير،
  ويحتاج مسار سيرفر مستقل إن طُلب.
- حفظ "إعدادات الشحن" في `settings/siteSettings` (صفحة القسائم):
  بقي من المتصفح؛ قراءتها عامة فتعمل، لكن حفظها للموظفين مرفوض
  في القواعد (التحديث مقصور على مفاتيح `counters`) — يحتاج مسار
  سيرفر مستقل إن طُلب.
- صفحة الأعضاء ونموذج الإضافة بالـ UID: لم تُمس.
- لا تغيير في `rbac.js` ولا أدوار متعددة (PR مستقل لاحقًا)،
  ولا تغيير في الإشعارات، ولا في الـ Checkout/الدفع/Webhook.

## ⚠️ التحقق الحي المطلوب بعد النشر (لم يُنفَّذ بعد)

1. سجّل دخول بحساب تجريبي بدور **أدمن** وبدور **orders** وبدور
   **viewer** (حساب منفصل لكل دور أو تغيير الدور مع إعادة الدخول):
   - صفحة الطلبات تعرض الطلبات، و"تحميل المزيد" والتصدير يعملان.
   - صفحة العملاء تعرض العملاء، و"تحميل المزيد" والتصدير يعملان.
   - صفحة الشحن وأكواد الخصم تعرض الأكواد **بدون** رسالة
     "فشل تحميل البيانات"، وإنشاء/تعديل/حذف كود يعمل لدور
     `content`/`admin` ويُرفض (403) لدور `viewer`.
   - صفحة العروض: حفظ/تفعيل/حذف عرض وحفظ قاعدة الشحن يعمل
     لدور `content`/`admin`.
2. تأكد أن دور `viewer` يرى القوائم ولا يستطيع الحفظ (الواجهة
   تحجب أزرار الحفظ أصلًا، والـ API يرد 403).
3. راقب سجلات السيرفر لأي `orders_list_failed` أو
   `promotions_list_failed` بعد أول دخول موظف.
